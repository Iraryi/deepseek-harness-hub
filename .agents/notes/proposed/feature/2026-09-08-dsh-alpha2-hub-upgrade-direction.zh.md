# Agent Note: DSH Alpha.2 面向 HUB 的升级方向

Status: proposed

[English](2026-09-08-dsh-alpha2-hub-upgrade-direction.md) | 中文

## Problem

上游 DSH 发布的变化不只是版本号：Alpha.2 增加或调整了能力包、Client 与 Host 的包边界、会话控制、Web 启动行为和发布元数据。HUB 必须在不静默启用实验能力、不丢失已安装组件记录、不退回到未经核验的本地包的前提下，把这些变化展示给用户。

## Proposal

HUB 把上游发布视为能力差异输入，并分别维护 DSH、HUB 以及每个已安装组件的版本轨道。发布记录保存上游提交、源码压缩包摘要、运行时清单摘要、Client 产物摘要，以及 Setup 页面使用的兼容性结果。

### P0 — 接入与恢复

- 发布更新前比较上游包图、配置文件、配置包、CLI 命令、Web patch 清单和运行时清单与上一个固定版本的差异。
- HUB 展示 DSH 版本、HUB 版本、Setup schema、配置文件、平台和已安装组件的兼容矩阵；未知或实验能力保持手动选择。
- 更新、修复、卸载是三个独立操作。除非用户明确选择删除数据，否则三者都保留 `%LOCALAPPDATA%\DeepSeekHarness`、已安装组件库和会话数据。
- 每次更新先在现有安装旁边暂存，核验摘要和必要入口，再原子切换并写入回滚记录。切换失败时继续使用现有安装。

### P1 — 能力感知的 HUB

- 增加更新中心，按用户可见能力归组上游变化：完全能力包、队列与引导控制、子代理与任务、会话历史与统计、Web 重连与旧资源恢复、以及在应用中打开的集成。
- 由配置文件声明实际消费的能力，而不是根据包是否存在推断。HUB 分别报告缺失、不兼容、已禁用和用户启用的能力。
- HUB 子插件默认与 Desktop 隔离。组件如需接入 Desktop，必须明确申请；审阅页显示受影响界面、重启要求、权限、网络使用和回滚范围。
- 以已安装组件库作为权威来源。刷新目录可以改变发现结果，但不能把已经安装的组件变成“仅本地”或“缺失”。

### P2 — 稳健的 Setup 与 Web 体验

- 在线传输、缓存复用、手动选取文件、核验、激活和回滚统一使用一套 Setup 进度协议。每次传输显示字节子进度、当前日志、取消状态和可重试的失败原因。
- 立即显示内置或缓存目录，再后台刷新；在线来源不可用或格式错误时保留最后一个可用快照。详情页保留页码、筛选条件和滚动位置。
- Web 启动采用有上限的就绪状态，提供可操作的重试和重启。旧 Client 资源只执行一次缓存恢复，随后给出诊断结果，不进入无限转圈。
- Desktop、HUB、CONFIG 和 Setup 使用一致的视觉语言：独立任务栏身份、圆角界面、不遮挡、不闪烁的选中态，以及无空白的切换过程。

### Release gates

基于 Alpha.2 的 HUB 发布必须通过源码和包依赖检查、Host 与 Client 类型检查、HUB 和首次启动专项测试、Web 生产构建、Launcher 构建、隔离运行时就绪测试、更新/修复/卸载数据保留测试、离线目录回退、手动依赖导入和回滚核验。任何发布任务都不得运行会修改宿主 Shell Folders 注册表的 smoke 测试；临时测试状态必须同时由看门狗和 `finally` 清理并恢复。

## Alternatives considered

**只替换上游源码树。** 这样能更新包代码，却会让 HUB 清单、Setup 证据、配置文件选择和恢复行为继续过时。否决，因为用户看到的契约横跨运行时、Web Client 和安装器。

**默认启用所有 Alpha.2 能力。** 这会让首次启动不可预测，也可能在配置文件不兼容时激活实验包。否决；能力声明和选择状态应归配置文件与 HUB 审阅流程管理。

**让在线目录决定已安装状态。** 在线刷新失败会让正常工作的本地组件看似缺失，并可能诱导用户进行破坏性重装。否决；已安装组件库和配置记录保持权威。

**原地更新，失败后再修复。** 部分替换会留下难以诊断的 DSH/HUB 混合图。否决；暂存核验与原子切换提供明确且有限的回滚点。

## Acceptance criteria

- 上游发布记录包含精确源码提交和摘要，HUB 分开显示 DSH 与 HUB 版本。
- 配置文件可以明确消费 Alpha.2 能力；不支持或实验能力保持禁用，并显示其状态。
- 更新、修复、卸载、重装和回滚默认保留已安装组件记录与用户数据。
- 目录失败、Web 旧资源、Setup 传输中断和激活失败都产生有上限、可重试、带证据的状态。
- 发布门禁在隔离目录中实测安装路径，并且结束后没有应用进程、Shell Folders 修改或测试数据残留。

## Risks

如果能力元数据靠手工维护，就可能与上游包行为漂移；发布流程必须从清单生成包和配置文件部分，并对未审阅的差异失败。Alpha.2 的变化可能要求社区旧组件使用兼容适配器，但适配器不得削弱已安装组件库的权威性或数据保留保证。完全能力配置文件会增加下载量和启动工作，因此 HUB 必须让它保持手动选择，并在激活前显示资源成本。
