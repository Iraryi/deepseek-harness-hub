# Agent Note: Setup HUB 与审核型 Setup 库

Status: implemented

[English](2026-08-15-setup-hub-and-library.md) | 中文

## 问题

桌面用户需要通过同一个安装界面处理内置能力包、固定 Commit 的 GitHub 插件和独立发布的 Setup EXE，同时不能混淆这些形式，也不能要求系统预装开发环境。GitHub 热度与维护者自行书写的徽章不能替代来源、许可证、资产、签名、权限、网络和审核证据。

如果 HUB 把可变的软件包名或 Git 引用直接交给包管理器，源码就可能在审核和安装之间发生变化。如果独立 Setup 不展示同样的证据，它又会成为绕过 HUB 的弱路径。

## 决策

Web/Desktop 的插件设置包含 DSH HUB，安装前会渲染共用 Setup 清单。Windows 还会把 `dsh-hub.exe` 作为基于同一套受签名 Web Runtime 的独立全窗口入口交付；它不会打开外部浏览器，会通过原生桥打开 CONFIG，并把普通 `dsh.exe` Desktop 作为独立的同级进程启动。本体与 HUB 使用不同的单实例互斥锁、本地服务端口和 EXE 图标，两者的 WebView 与托盘右键菜单都能打开另一入口。本体保留配置端口，HUB 始终申请动态回环端口。HUB 子服务默认使用 `hub/runtime-home`，因此本体侧栏与 Web UI 插件不会进入 HUB；只有 CONFIG 中的显式选项会共享本体 profile。CONFIG 提供圆角双行产品选择器，并把本体设置写入 `config.json`、HUB 设置写入 `hub-config.json`；HUB 独立管理跟随系统、浅色或深色主题、启动功能区、默认发现来源、加载画面、关闭行为和专用托盘按钮。产品选项会在侧栏内展开。切换时，CONFIG 会在暂停原生重绘期间构建隐藏的替代界面，移除旧界面后再以一次同步重绘使整窗及全部子控件失效。替代界面显示前，CONFIG 会通过 `GetDpiForWindow` 缩放 WinForms 不会为动态新增控件自动重算的边距、表格绝对尺寸和固定控件尺寸。这样既不会再访问已释放的原生菜单，也不会暴露半成品帧、高 DPI 位图残影、切换后控件退回 96 DPI 大小或改变普通／最大化窗口边界。两个启动器只会在 Node 进程报告 `dsh web` 之前持有独占文件锁，从而串行化同时启动时的 profile 修复与端口选择，而不会共享运行中的进程或服务。每个互斥锁都有带提醒与静默两种命名激活事件：用户直接重复启动 EXE 时会恢复运行中的窗口并提示，应用内部的同级入口命令则只静默恢复和前置窗口。该机制既防止从无边框 Desktop 启动的 HUB 隐藏在它后面，也不会打断正常的右键切换或 HUB 返回操作。HUB 始终进入普通窗口模式，不会继承 Desktop 的无边框或真全屏模式。在加载、托盘恢复与静默激活时，它会启用 `ShowInTaskbar`、加入 `WS_EX_APPWINDOW`、移除 `WS_EX_TOOLWINDOW` 并刷新原生窗口框架，因此从 Desktop 托盘打开的 HUB 拥有自己的任务栏按钮。响应式布局会在空间受限时移除次要导航，并在控件发生遮挡前把较宽的分类与信任筛选条替换成原生下拉框。清单区分 HUB 代安装的虚拟 Setup 与独立可执行 Setup，并记录不可变来源、许可证条款、签名声明、审核状态、兼容范围、权限、网络行为和资产 SHA-256。非认证条目必须先完成浏览器确认，再通过一次原生确认。WebView2 桥只接受当前回环应用来源、限制请求大小与并发，并负责安装进程树的生命周期。

profile 软件包安装通过 `artifactId` 引用一个 `package` 或 `archive` 资产。CLI 接受带或不带 UTF-8 字节顺序标记的 Setup 清单，兼容 Windows 工具常见的写入形式；随后把 HTTPS 资产下载到按内容寻址的缓存，验证 SHA-256，并且只把校验后的本地文件交给 npm。Windows Runtime 在私有 Node.js 旁携带 npm，因此 Setup 安装不会从 PATH 查找 npm 或 pnpm。除非展示出的清单声明 `install-scripts`，否则 npm 生命周期脚本保持禁用。

独立的 `deepseek-harness-setups` 仓库负责 GitHub 自动发现、草案与隔离状态、公开目录投影、审核与 SBOM 记录，以及通用 Inno Setup 引擎。发现流程会把默认分支固定到 Commit、计算源码压缩包哈希、检查许可证与软件包元数据，并且绝不自动授予认证。独立 EXE 内置同一份清单与证据，非认证软件必须显式接受，并调用已安装 Desktop 的 CLI；进入认证 Release 的资产还必须完成 Authenticode 签名。

Desktop 会把经过校验的审核目录放进受签名保护的 Web 资产。审核目录本身具备可信分发前，不启用在线认证等级刷新，因此远程 JSON 文件不能自行制造可信证书状态。除此之外，HUB 会携带 `awesome-dsh-plugin` 社区目录的 CC0 快照，并以在线刷新、本机缓存和随包快照三级方式读取这份发现元数据。社区元数据永远不能声明认证。

独立 HUB 使用功能区，而不是把分类当成产品的主要结构。主页汇总本地库、离线收件箱、已登录 GitHub 账户的 Star 和安装记录。GitHub 凭据只存在于独立账户功能区；发现页与 Star 页不会渲染令牌输入框。GitHub 全域发现由原生启动器调用官方仓库搜索 API；账户与 Star 列表则使用用户提供、并由 Windows DPAPI 加密的令牌。WebView 永远不会收到保存的令牌。

DSHMK 是第一顺位与默认发现来源。原生启动器会同步它的在线目录与详情元数据、动态标签、验证记录、安装参考、源码链接、相关项目和图形资产，写入最近一次可用缓存，并在网络或来源数据不可用时回退到随程序携带的 2,888 项快照。目录候选会按生成时间、仓库数量与一键安装覆盖率排序，并拒绝能力突然低于健康缓存或内置快照的刷新结果。目录读取使用有界尝试、取消、畸形数据拒绝与过期缓存回退，不会留下空页面或永久转圈。搜索区保持排序可见，并把搜索范围、动态 TAG／分类、项目类型、验证与安装能力、仅本地构建和每页数量收进一个圆角分层筛选面板。客户端会持久保存 12、24、48、96 或 200 条分页，并在关闭重构后的侧边详情、主题模态层或全画面详情后恢复进入前的查询、筛选、页码和滚动位置。卡片默认使用独立的“项目详情”按钮进入详情；CONFIG 可以恢复整卡点击，并且独立改为显示承载在应用内的原网站内容。

其余发现来源吸收了 MIT 许可 `dsh-market` 已验证的面向用户思路：大型精选目录、多语言分类、搜索、热度与时间排序、时间筛选、分页、可安装状态、在线／缓存／离线来源标识和直接安装路径。社区精选市场排在 DSHMK 之后，作为可通用安装的来源；GitHub 全域只承担候选发现。只有原生预检能够证明精确来源与安装计划时，HUB 才提供一键 Setup；GitHub 全域结果可以创建本地构建草稿，但不能绕过这条路径。HUB 不执行目录中的命令文本。原生所有者会解析固定 GitHub Commit 或 npm Release，拒绝不支持的下载主机与无法通用证明的 monorepo 子目录，限制资产为 256 MB，计算 SHA-256，把文件放入内容寻址 Setup 缓存，再返回标准清单。具备 npm 包的条目会直接核对精确包名、不可变版本、tarball、生命周期脚本、许可证和已发布的 `gitHead`，不依赖 GitHub 未登录 API 的公共配额；源码压缩包仍必须通过 GitHub 解析固定 Commit。Setup 进度界面随后负责有界预检、下载、解压、依赖安装、profile 修改、Bundle 激活、安装后验证、日志、取消、重试与最终复位。总体阶段进度条与下载子进度条相互独立；后者由 CLI JSON Lines 字节事件或原生预下载回调驱动，在总量已知时显示已下载字节、总字节和百分比，总量未知时保持不定状态，而且从原生预下载切换到 CLI 时会从已完成下载阶段或更高位置继续，不会让总进度倒退。在获取阶段，一个低调的手动下载面板会列出每个所需资产的准确文件名、声明大小、下载地址、源仓库和已有 SHA-256。用户选择的本地文件只有在原生所有者检查 256 MB 上限、声明大小、gzip／ZIP／可执行文件头与声明 SHA-256，并计算内容哈希、原子写入同一内容寻址缓存后，才能进入当前请求。导入成功会取消竞争中的在线传输并继续安装；在线失败会保留请求以等待导入，而取消操作会同时终止两条路径。只有拥有待处理请求的当前操作会旋转图标。成功激活会写入收据并持久显示醒目的本体重启入口；它只静默重启 Desktop 自己拥有的 Node 服务，HUB 保持运行。真实隔离冒烟会通过打包 Runtime 把一个 npm 支持的精选条目安装到临时 web profile。它使用专门的无界面数据模式跳过 WebView2、托盘、计时器和窗口资源，因此安装断言能够正常结束并删除临时 profile。无法通过通用证明的项目改为创建本地构建工作区；AI 只用于这条本地构建与排错路径。

精选卡片会把 GitHub 所有者图片作为插件图形；图片不可用时回退为中性插件图形，绝不显示文字首字母。独立 HUB 的深色界面采用与 `dsh-market` 相同的语义表面层级：应用栏与工作区使用抬高的第二层，内容卡片使用更安静的第一层，悬停或选中控件使用第三层。原有的 Setup 市场勾选图标继续只作为导航图标，不会被当作插件图形。

Desktop 可能承载为更宽浏览器画面设计的第三方设置插件。启动器只会在识别出的 `dsh-market` 根节点下安装窄范围兼容样式：已安装卡片的说明内容占据完整的可换行行，开关、链接和移除操作则组成独立的下一行。CSS 注入会等待 `document.head` 或文档根元素可用，因此较早执行的 WebView2 文档创建回调也会保留兼容 CSS 与用户配置的注入 CSS。

启动器在自身数据目录下负责一个本地 `hub` 根目录。可编辑工作区包含 Setup 清单、选项 schema 和面向 AI 辅助编辑的双语约束。Desktop 设置入口只作为组件管理器展示已安装记录、预备工作区与离线包；发现新组件仍由独立 HUB 负责。profile 安装成功后会建立持久记录并保存最近一次安装清单。内置 bundle 通过修改 profile bundle 列表移除；软件包 Setup 会记录安装时新增的依赖，先使用 Runtime 私有 npm 移除，再协调 bundle 列表。除非存在经过审核的卸载器，可执行 Setup 不会声称支持自动移除。

移除由 Setup 管理的组件后，界面会把 Desktop 服务标记为需要重启，并打开立即重启或稍后重启的选择面；选择稍后会保留持久重启入口。Shell 自有的插件加载错误页也提供当前宿主重启操作。两条路径都会立刻用极简的“重启中”转圈替换陈旧内容；WinForms 启动器在工作线程停止 Node 服务，并让双缓冲的原生重启层持续响应，直到收到结构化 Web UI 就绪状态或终止失败。Desktop 与 HUB 使用不同的显式 AppUserModelID；HUB 还会清除原生 owner 并重新声明应用窗口任务栏样式，因此从 Desktop 打开 HUB 会产生独立任务栏按钮，而不是只在托盘中增加进程。

## 考虑过的替代方案

**把任意 GitHub 仓库编译成 EXE。** 仓库结构、许可证、构建脚本和运行行为并不统一，EXE 外壳也不会让未经审核的源码变得可信。因此自动发现只生成 Setup 界面与隔离证据，不生成认证结论。

**使用系统包管理器。** 这会让小白安装依赖可变的 PATH 状态，重新引入 Desktop Runtime 已经消除的环境故障。因此 Runtime 自带私有 npm。

**信任 Star 或清单中的认证字段。** 热度不能证明来源和安全安装，自行声明的 JSON 也没有经过认证。信任等级只能来自受交付包保护的证据，或未来经过签名的目录。

## 后果

用户会在 HUB 与 EXE 安装中获得一致的证据优先流程，并且可以在不依赖系统包管理器的情况下执行安装。Runtime 会因携带 npm 而增大，每个软件包资产也必须在安装前能够下载和计算哈希。缺少可再分发许可证、DSH bundle 声明、公开软件包或完整行为审核的源码仓库只会保留在隔离记录中，不会在用户电脑上静默失败。

GitHub OAuth 设备流会等到项目注册 OAuth App 并获得客户端 ID 后再实现。因此访问令牌连接是一项明确的本地兼容方案，而不是伪装成 OAuth 登录。
