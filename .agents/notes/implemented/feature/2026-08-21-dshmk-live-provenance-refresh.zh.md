# Agent Note：缓存首屏后的 DSHMK 在线来源刷新

Status: implemented

[English](2026-08-21-dshmk-live-provenance-refresh.md) | 中文

## 问题

DSHMK 目录增长到超过启动器原先的 16 MiB 响应上限，同时在线请求只有 16 秒时限。因此 HUB 每次启动都会选择本机快照。即使后台刷新后来成功，页面也没有收到通知，来源徽标仍会停留在本机缓存。

## 决策

启动器将当前 DSHMK 目录响应上限提高到 32 MiB，并为第一方在线端点提供有界的四分钟传输窗口。备用 raw 目录仍使用较短的 45 秒时限，并继续接受现有的覆盖量回退保护。有缓存时仍然立即首屏显示，以保证离线可用；后台刷新成功后，原生层发送一个小型 WebView 事件，DSHMK 页面重新请求当前页并把来源徽标更新为在线，同时保留筛选、页码、详情状态和原生窗口。

显式刷新绕过内存 TTL，并在同一有界传输中发送 HTTP Cache-Control 重新验证请求。并发刷新调用共用一个尚未完成的原生任务。界面在传输和失败期间保留可用卡片。来源生成时间仍由发布方决定；同步时间记录成功获取的时刻。读取持久化来源记录不会把磁盘数据变为在线数据，避免刷新控件和在线徽标宣称未经网络响应证实的新鲜程度。

目录选择优先比较来源生成时间，再比较仓库数量。条目明显减少的候选只有在生成时间更新、保留安装能力、包含至少 100 个唯一有效 GitHub 仓库，且声明获取数量与完整仓库数组一致时才被接受。更旧快照、数量不一致和严重能力下降仍会被拒绝，避免仅凭条目数量把更新的精选目录锁在较大的旧快照之后。可用缓存采用本地化的非阻断提示并折叠诊断，而不是显示页面不可用错误。

## 验证

启动器构建必须同时编译原生桥接与 WebView 页面；GUI 测试覆盖没有 WebView2 时订阅函数是安全空操作。实机验证检查更新后的启动器能读取现有目录缓存，在网络可用时刷新在线来源，并在刷新成功后发送 `dsh-hub-catalog-updated`。本次不重建 Setup EXE。

隔离的 CatalogRefreshHarness 覆盖绕过缓存、并发复用待完成传输、离线恢复和保留来源生成时间。客户端测试覆盖显式刷新、可见的等待反馈、失败后保留卡片，以及普通筛选请求不残留强制刷新标记。这些检查不能替代安装目录或在线来源测试。

9 月 29 日的隔离原生回归接受完整的较新子集，拒绝更旧、数量不一致、重复及过小快照；重新选择目录时仍保留较新缓存。在全新 D: 测试目录中通过真实生产桥接刷新，返回 2,500 个仓库，来源生成时间为 `2026-09-29T15:34:00.073Z`。构建后客户端测试覆盖中英文缓存失败提示、折叠诊断、单个重试控件和成功在线刷新。这些测试不修改宿主安装或用户配置目录。

## Alternatives considered

**改成只使用在线首屏：** 放弃，因为 DSHMK 端点缓慢或不可达时，会让 HUB 在离线和网络降级环境中显示为空或不可用。

**静默完成在线刷新，等下次启动才显示：** 放弃，因为用户仍会看到过期的“本机缓存”来源徽标，也不知道当前目录其实已经刷新成功。

## Consequences

第一次在线请求可能比普通目录请求更慢，但有明确的超时，并且不会阻塞缓存首屏。刷新成功后只在当前页面内重新请求数据；筛选、页码、详情、滚动位置和原生窗口几何状态仍由现有 HUB 状态保持。
