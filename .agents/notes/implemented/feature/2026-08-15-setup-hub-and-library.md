# Agent Note: Setup HUB and reviewed Setup library

Status: implemented

English | [中文](2026-08-15-setup-hub-and-library.zh.md)

## Problem

Desktop users need one installation surface for in-box capability packs, pinned GitHub plugins, and independently released Setup EXEs without confusing those forms or requiring a system development environment. GitHub popularity and maintainer-authored badges cannot substitute for source, license, artifact, signature, permission, network, and audit evidence.

A HUB that forwards mutable package or Git references directly to a package manager would allow source changes between review and installation. A standalone Setup that omits the same evidence would create a weaker path around the HUB.

## Decision

The Web/Desktop plugin settings include DSH HUB, which renders the shared Setup manifest before installation. Windows also ships `dsh-hub.exe` as a dedicated full-window entry over the same signed Web runtime; it does not open an external browser, opens CONFIG through the native bridge, and starts the normal `dsh.exe` Desktop as a separate sibling process. Desktop and HUB use distinct single-instance mutexes, local-service ports, and executable icons, while each WebView and tray context menu can open the other entry. Desktop retains the configured port and HUB always reserves a dynamic loopback port. HUB runs its child service against `hub/runtime-home` by default, so Desktop sidebar and Web UI plugins do not enter HUB; CONFIG provides the only opt-in that shares the Desktop profile. CONFIG exposes a rounded two-line product selector and stores Desktop settings in `config.json` and HUB settings in `hub-config.json`; HUB independently owns its system, light, or dark theme, initial function, preferred discovery source, loading presentation, close action, and dedicated tray-button preference. Product choices expand inside the sidebar. Switching builds a hidden replacement surface while native redraw is suspended, removes the old surface, and then invalidates the full window and every child in one synchronous frame. Before that surface becomes visible, CONFIG uses `GetDpiForWindow` to scale padding, absolute table metrics, and fixed control sizes that WinForms does not automatically rescale for dynamically added controls. This avoids disposed native menus, partially constructed frames, high-DPI bitmap ghosts, 96-DPI control shrinkage after switching, and changes to normal or maximized window bounds. Both launchers take an exclusive file lock only until their Node process reports `dsh web`; this serializes profile repair and port selection during simultaneous startup without sharing the running process or service. Each mutex has notice and silent named activation events: a direct duplicate EXE launch restores the running window with a notice, while internal companion commands restore and foreground it silently. This prevents a HUB started from a borderless Desktop from remaining hidden behind it without interrupting normal right-click switching or the HUB return action. HUB always enters its normal window mode instead of inheriting Desktop's borderless or exclusive mode. On load, tray restore, and silent activation, it sets `ShowInTaskbar`, adds `WS_EX_APPWINDOW`, removes `WS_EX_TOOLWINDOW`, and refreshes the native frame, so a HUB opened from the Desktop tray has its own taskbar button. The responsive layout removes secondary navigation when space is constrained and replaces wide category and trust strips with native selectors before controls can overlap. The manifest distinguishes a HUB-managed virtual Setup from a standalone executable Setup and records immutable source provenance, license terms, signature claims, audit status, compatibility, permissions, network behavior, and artifact SHA-256 values. Non-certified entries require browser acknowledgement and a second native confirmation. The WebView2 bridge accepts only the active loopback application origin, limits request size and concurrency, and owns the installation process tree.

Profile package installation names a `package` or `archive` artifact by `artifactId`. The CLI accepts UTF-8 Setup manifests with or without the byte-order mark commonly written by Windows tools, downloads the HTTPS artifact into a content-addressed cache, verifies SHA-256, and gives only the verified local file to npm. The Windows Runtime carries npm beside its private Node.js executable, so Setup installation does not search PATH for npm or pnpm. npm lifecycle scripts are disabled unless the displayed manifest declares `install-scripts`.

The independent `deepseek-harness-setups` repository owns automated GitHub discovery, draft and quarantine states, the public registry projection, audit and SBOM records, and a generic Inno Setup engine. Discovery pins the default branch to a commit, hashes the source archive, inspects license and package metadata, and never grants certification. Standalone EXEs embed the same manifest and evidence, require explicit acceptance for non-certified software, and call the installed Desktop CLI; certified Release assets additionally require Authenticode signing.

The Desktop ships a validated reviewed registry inside its signed Web assets. Live remote certification refresh remains disabled until the reviewed registry itself has authenticated distribution, so a remote JSON file cannot invent a trusted certificate state. Separately, HUB carries a CC0 snapshot of the `awesome-dsh-plugin` community directory and refreshes that discovery metadata online with local-cache and bundled-snapshot fallback. Community metadata never asserts certification.

The dedicated HUB uses functional navigation rather than treating categories as the product's primary structure. Home summarizes the local library, offline inbox, authenticated GitHub stars, and installed records. GitHub credentials live only in a dedicated account function; discovery and starred views never render token inputs. Global GitHub discovery calls the official repository search API from the native launcher, while authenticated account and starred-repository calls use a user-supplied token encrypted with Windows DPAPI. The WebView never receives the stored token.

DSHMK is the first and default discovery source. The native launcher synchronizes its live catalog and detail metadata, dynamic tags, validation records, installation references, source links, related projects, and icon assets, writes a last-known-good cache, and falls back to a bundled 2,888-entry snapshot when the network or source data is unavailable. Catalog selection ranks candidates by generation time, repository count, and one-click-install coverage, and rejects a refreshed source whose capability suddenly collapses below a healthy cache or bundle. Catalog reads use bounded attempts, cancellation, malformed-data rejection, and stale fallback instead of leaving an empty page or permanent spinner. Search keeps sorting visible while a rounded filter surface groups search scope, dynamic TAG/category, project type, validation and installability, local-build-only state, and page size. The client persists page sizes of 12, 24, 48, 96, or 200 and restores the originating query, filters, page, and scroll position after closing a reconstructed detail side panel, themed modal, or full-surface route. A dedicated Details button is the default card entry; CONFIG can restore whole-card activation and independently select contained original-site content instead of the reconstructed detail.

The remaining discovery sources incorporate proven user-facing ideas from the MIT-licensed `dsh-market`: a large curated registry, localized categories, search, popularity and recency sorting, time filters, pagination, installability state, online/cache/offline provenance, and a direct install path. The curated Setup market follows DSHMK as the generic-install source, while Global GitHub remains candidate discovery. HUB offers one-click Setup only when native preflight can prove the exact source and installation plan; a Global GitHub result can create a local builder draft but cannot bypass that path. HUB does not execute catalog command strings. The native owner resolves an immutable GitHub commit or npm release, rejects unsupported hosts and generic monorepo subpaths, enforces a 256 MB artifact limit, computes SHA-256, seeds the content-addressed Setup cache, and returns a standard manifest. npm-backed entries verify the exact package identity, immutable version, tarball, lifecycle scripts, license, and published `gitHead` without depending on the unauthenticated GitHub API quota; source archives still require GitHub commit resolution. The Setup progress surface then owns bounded preflight, download, extraction, dependency installation, profile mutation, Bundle activation, post-install verification, logs, cancellation, retry, and terminal reset. Its overall stage bar is separate from a download sub-bar driven by CLI JSON-lines byte events or the native pre-download callback; known totals show transferred bytes and percentage, unknown totals remain indeterminate, and the handoff from native pre-download to the CLI starts at or above the completed download stage rather than moving backward. During that acquisition stage, a subdued manual-download panel exposes each required artifact's exact file name, declared size, download address, source repository, and available SHA-256. A selected local file enters the active request only after the native owner enforces the 256 MB limit, declared size, gzip, ZIP, or executable header, and declared SHA-256, computes its content hash, and atomically seeds the same content-addressed cache. A successful import cancels the competing online transfer and continues installation; an online failure keeps the request available for import, while cancellation terminates both paths. Only the active pending operation animates its icon. Successful activation records a receipt and persists a prominent Desktop-restart action; that action silently restarts the Desktop's owned Node service while HUB remains open. A real isolated smoke installs one npm-backed curated entry into a temporary web profile through the packaged Runtime. Its dedicated headless data mode skips WebView2, tray, timer, and window resources so the install assertion terminates cleanly and removes the temporary profile. Entries that cannot satisfy the generic proof path create local builder workspaces instead; AI is reserved for that local construction and troubleshooting path.

Curated cards request the GitHub owner image as their plugin artwork and fall back to a neutral plugin glyph, never a text initial. The dedicated HUB dark presentation follows the same semantic surface hierarchy as `dsh-market`: the application chrome and workspace use the raised second layer, content cards use the quieter first layer, and hover or selected controls use the third layer. The existing Setup-market check icon remains navigation chrome and is not repurposed as plugin artwork.

Desktop can host third-party settings plugins whose compact rows were designed for a wider browser surface. The launcher installs narrowly scoped compatibility CSS only under the detected `dsh-market` root: installed-card descriptive content occupies a complete wrapping row, while switches, links, and removal actions form a separate row. CSS injection waits until `document.head` or the document element exists, so an early WebView2 document-created callback retains compatibility CSS and user-configured injected CSS.

The launcher owns a local `hub` root beneath its data directory. Editable workspaces contain the Setup manifest, an options schema, and bilingual constraints for AI-assisted editing. The Desktop settings entry is a component manager over installed records, prepared workspaces, and offline packages; discovery remains in the independent HUB. Successful profile installations create durable records and preserve the last installed manifest. In-box bundles are removed by editing the profile bundle list; package Setups record dependencies added by installation and remove them with the Runtime's private npm before reconciling the bundle list. Executable Setups do not claim automatic removal unless a reviewed uninstaller is available.

Removing a Setup-managed component marks the Desktop service as restart-required and opens an immediate-or-later decision surface; deferral preserves the persistent restart action. The shell-owned plugin failure page also provides a current-host restart action. Both paths replace stale content with a minimal `Restarting` spinner, while the WinForms launcher stops its Node service on a worker thread and keeps a double-buffered native restart overlay responsive until structured Web UI readiness or terminal failure. Desktop and HUB set different explicit AppUserModelIDs, and HUB clears native ownership while reasserting app-window taskbar styles, so opening HUB from Desktop produces a separate taskbar button rather than only a tray process.

## Alternatives considered

**Compile arbitrary GitHub repositories into EXEs.** Repository layouts, licenses, build scripts, and runtime behavior are not uniform, and an EXE wrapper would not make unreviewed source trustworthy. Automated discovery therefore produces Setup views and quarantine evidence, not certification.

**Use the system package manager.** This makes novice installation depend on mutable PATH state and recreates the environment failures the Desktop Runtime removes. The Runtime carries its own npm instead.

**Trust stars or a manifest's certification field.** Popularity does not prove provenance or safe installation, and self-asserted JSON is not authenticated. Trust remains derived from evidence protected by the shipped distribution or a future signed registry.

## Consequences

Users receive one consistent evidence-first flow for HUB and EXE installation, including offline-capable package-manager execution. The Runtime grows because it carries npm, and every package artifact must be downloadable and hashable before installation. Source repositories that lack a redistributable license, a DSH bundle declaration, a public package, or completed behavior review remain visible only in quarantine records rather than silently failing on user machines.

GitHub device-flow OAuth remains deferred until the project owns a registered OAuth App and client ID. The access-token connection is therefore an explicit local fallback, not a simulated OAuth login.
