# 架构

[English](architecture.md) | 中文

DeepSeek Harness HUB 将发现、证据、安装和 Runtime 所有权分开，避免市场结果无声地变成安装承诺。

## 数据流

1. **来源适配器**读取 DSHMK、精选源、GitHub 发现、GitHub Star、离线包和本地创作目录。
2. **规范化**把各来源字段映射为稳定的项目、发布者、分类、兼容性和安装候选模型。
3. **证据解析**记录每条安装命令的来源、目标版本／引用以及已经运行的校验阶段。
4. **Setup 渲染**把合格候选转换成一致的多步骤 Setup 体验。
5. **执行**通过 Desktop 原生桥接完成，不通过任意浏览器 DOM 代码执行。
6. **库存**分别记录准备中的组件和已安装组件，并关联到 Desktop 或 HUB 配置范围。

## 进程边界

`dsh.exe` 与 `dsh-hub.exe` 是两个独立的原生进程，拥有各自的任务栏身份、配置范围、窗口状态和单实例通道。从一个进程打开另一个进程时，应聚焦已有进程，而不是弹出重复实例警告。

本地服务 Runtime 由作业／进程生命周期控制器负责。重启和卸载只能停止所选安装对应的服务树。

## 目录优先级

默认来源顺序是：

1. 从 DSHMK 得到的已验证项目和安装参考。
2. 带维护者证据的精选 Registry 条目。
3. GitHub 全域发现和用户 Star 的仓库。
4. 本地及离线包。

来源顺序影响排序和可信度，但不决定项目能否展示。动态来源标签在 Runtime 中规范化，同时保留一小套可离线使用的基准分类。

## 安装边界

虚拟 Setup 配方和独立 Setup EXE 共享展示概念，但信任级别和执行机制不同。详见 [Setup 包规范](setup-package-spec.md)。
